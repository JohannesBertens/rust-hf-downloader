# Plan: `rust-hf-downloader update` — in-app self-update

**Status:** implemented in **v2.10.0** (CLI + CI manifest; TUI phase 2 — startup
check + badge notification — remains future work)
**Goal:** `rust-hf-downloader update` checks for a newer release, downloads the
matching platform binary, verifies its SHA256, and swaps the running
installation in place — the v2.8/v2.9 one-liner installers, expressed in Rust,
so users never need to re-run a shell command. The TUI shows the current
version in the top bar (shipped in v2.10.0) and later flags available updates.

---

## 0. Research summary (what the ecosystem does)

| Approach | Evidence | Fit for this repo |
|---|---|---|
| **`self_update` crate** (jaemk, 0.44/1.3.0, ~12M downloads, maintained 2026-09) | GitHub/GitLab/Gitea/S3/**static-manifest** backends; re-exports `self_replace`; builder API `Update::configure()` | Good, but its GitHub backend rides `api.github.com` (60 req/hr anon, token-gated beyond) and it does **not** verify against a published checksums file. We already have reqwest+sha2+hex in-tree and a SHA256SUMS convention. |
| **`self_replace` crate** | The canonical binary swap: Unix = plain `rename(2)` over a running exe (inode swap; `ETXTBSY` only bites writes, never renames); Windows = rename running exe aside, move new one in, best-effort delete of the aside copy (same dance our `install.ps1` does) | **Adopt.** Tiny, battle-tested, exactly the swap semantics we need. |
| **Tauri updater / `latest.json` manifest** | Version+asset+signature manifest fetched from a URL you control; GitHub Releases serves `releases/latest/download/latest.json` from its CDN with **no per-IP rate limit** (unlike api.github.com) | **Adopt the manifest pattern.** Our stable asset names (v2.8.0) already make the CDN redirect work; a manifest adds the version metadata SHA256SUMS lacks. |
| **cargo-dist / `axoupdater` install receipts** | Receipt file written at install time discriminates "we own this file" (self-update) from brew/npm/cargo (print the right package-manager command) | **Skip for now.** Our v2.9.0 installers already took over `~/.cargo/bin` with that exact philosophy: wherever the binary lives, *we* replace it in place. A receipt adds state for little gain at this scale. |
| **`update-informer` crate** | Check-only (Crates.io/GitHub/...), caching | Superseded by the manifest approach; no new dep needed. |

**Decisions:**
1. Hand-rolled check/download/verify (reuses in-tree reqwest/serde/sha2/hex and
   our published `SHA256SUMS`/stable-asset infra) + **`self_replace`** for the
   atomic swap. `self_update` wholesale is rejected: API rate limits, no
   checksum verification, archive-format baggage.
2. **New release asset `latest.json`** generated by CI, served via the
   rate-limit-free CDN redirect — same trick that powers the installers.
3. Mirror support mirrors the installers: `RHD_UPDATE_BASE` env overrides the
   release base URL entirely (same contract as `RHD_DOWNLOAD_BASE`).
4. The TUI never swaps binaries under itself (Windows locks + ratatui state);
   it surfaces availability and defers to the CLI command.

## 1. Release-side prerequisite: `latest.json`

`.github/workflows/release.yml` release job gains one step after
`SHA256SUMS` generation (values already in `dist/` + the tag):

```jsonc
// served at releases/latest/download/latest.json
{
  "version": "2.10.0",                       // from the tag, no 'v'
  "released_at": "2026-09-30T12:00:00Z",     // workflow run timestamp
  "notes_url": "https://github.com/JohannesBertens/rust-hf-downloader/releases/tag/v2.10.0",
  "assets": {
    "x86_64-unknown-linux-gnu":  { "name": "rust-hf-downloader-x86_64-unknown-linux-gnu.tar.gz", "format": "tar.gz", "sha256": "…" },
    "aarch64-unknown-linux-gnu": { "name": "…tar.gz", "format": "tar.gz", "sha256": "…" },
    "aarch64-apple-darwin":      { "name": "…tar.gz", "format": "tar.gz", "sha256": "…" },
    "x86_64-apple-darwin":       { "name": "…tar.gz", "format": "tar.gz", "sha256": "…" },
    "x86_64-pc-windows-msvc":    { "name": "…zip",    "format": "zip",    "sha256": "…" }
  }
}
```

Generated with a small `jq`/heredoc step reading the existing `SHA256SUMS`;
uploaded alongside the other assets. Bootstrap note: releases **before** the
one that ships this file simply 404 the manifest — the client reports "no
update information available (pre-2.10.0 release?)" and suggests the
one-liner installer.

## 2. CLI: `update` subcommand

### 2.1 Interface (src/cli.rs)

```
rust-hf-downloader update            # check + download + verify + swap
rust-hf-downloader update --check    # report only (script-friendly exit code)
rust-hf-downloader update --force    # reinstall even if same version
```

- `Command::Update(UpdateArgs)` with alias `upgrade`.
- `--check` exits `EXIT_UPDATE_AVAILABLE` (new, appended to the existing
  exit-code table + docs) when newer exists, `0` when current — usable from
  the agent skill and CI.
- Human output follows the `download` subcommand's reporter style; a
  `--json` event stream (`checking`, `downloading {progress}`, `verified`,
  `swapped`, `up_to_date`, `error`) for script parity with `download --json`.
- Env overrides: `RHD_UPDATE_BASE` (default
  `https://github.com/JohannesBertens/rust-hf-downloader/releases/latest/download`),
  `RHD_NO_UPDATE_CHECK=1` for the TUI check (§4).

### 2.2 Module: `src/update.rs`

```
check()      -> UpdateInfo { current, latest, asset: &AssetSpec, notes_url } | Current | Unknown
run(args)    -> downloads to tempdir, verifies, extracts, self_replace::self_replace()
```

- **Version compare:** hand-rolled `VersionTriple {major, minor, patch}` +
  `Ord` (~20 lines, strict `x.y.z` — we control the tag format) with unit
  tests; no semver dep.
- **Target triple:** compile-time mapping via `cfg!(target_arch/target_os)`
  producing exactly the CI asset triple (unit test pins the const per
  platform).
- **HTTP:** own minimal `reqwest` client with 10s timeout (do **not** reuse
  `http_client.rs` — that one is HF-token-aware; update traffic must never
  send the HF token).
- **Verify:** stream asset to temp file, hash with `sha2`/`hex`, compare to
  manifest `sha256`. Mismatch → delete temp, exit with checksum error.
- **Extract:** single member from the archive — `tar.gz` (Unix assets) via
  cfg-gated `flate2`+`tar`, `zip` (Windows asset) via cfg-gated `zip` crate.
  Two small platform-gated deps; rejects archives containing anything other
  than exactly one `rust-hf-downloader[.exe]`.
- **Swap:** `self_replace::self_replace(current_exe, new_temp_path)` —
  Unix atomic rename; Windows rename-aside dance. Then verify by running
  `<exe> --version`? No — just report the manifest version; next launch is
  the proof (matches installer behavior).
- **Temp hygiene:** everything under `std::env::temp_dir()` + unique subdir,
  best-effort cleanup, no partial writes anywhere near the install dir.

### 2.3 Exit codes

| Code | Meaning |
|---|---|
| 0 | up to date, or update applied |
| existing `EXIT_NETWORK`-family | manifest/asset fetch failed (map like `download` does) |
| new `EXIT_UPDATE_AVAILABLE` | `--check` found a newer version |
| existing `EXIT_IO`-family | swap failed (permissions, locked file) |
| new `EXIT_CHECKSUM` | hash mismatch (mirrors the TUI's verify-failure concept) |

(Final placement follows the existing table in `src/cli.rs`; keep the
documented table in sync.)

### 2.4 Interaction with other install sources

Consistent with the v2.9.0 installer takeover philosophy: wherever
`current_exe()` lives, we replace it. Edge cases surfaced in output:

- Path not writable → error advising `sudo`-free relocation or the one-liner.
- Under `$CARGO_HOME/bin` → note that a future
  `cargo install rust-hf-downloader` would compile-from-source and overwrite;
  `cargo uninstall` is the clean handoff (same messaging as install.sh).
- System locations (`/usr/local/bin`, scoop shims) → attempt; on failure,
  print the package-manager-appropriate hint.

## 3. CI changes (one step, release job)

After `SHA256SUMS`, before `action-gh-release`: build `latest.json` from the
tag + parsed checksums (shell + `jq`, fail if any expected triple is
missing), add to the `files:` list. Asset names stay **version-free**
(load-bearing for the CDN redirect — do not regress).

---

## 4. TUI integration (phase 2, small)

- Top bar (filter toolbar) already shows `vX.Y.Z` flush-right (shipped with
  this plan's sibling change). When a cached update check says a newer
  version exists, the badge becomes `v2.9.0 → v2.10.0 available` (green).
- Background check on TUI start via `check()`, non-blocking (tokio spawn),
  **24h cache** persisted in config (`last_update_check` timestamp), config
  key `check_updates = true|false` (Options screen row), env
  `RHD_NO_UPDATE_CHECK=1` kills it entirely.
- `'u'` key (Normal mode, when update available) opens a confirm popup that
  spawns `<current_exe> update` as a detached child and exits the TUI
  cleanly (the child owns the terminal). The TUI itself never swaps the
  binary in-process.

## 5. Test strategy

- **Unit** (`src/update.rs` tests): manifest parsing (serde, malformed,
  missing asset), `VersionTriple` ordering, triple-const pinning, checksum
  formatting.
- **E2E** (extend `tests/` mock-server harness): serve `latest.json` + a
  fake-2.11.0 archive from a local HTTP server; copy the freshly built
  binary to a temp dir; run the **copy** with `RHD_UPDATE_BASE` pointed at
  the mock; assert `--version` now reports 2.11.0 and the temp-dir exe was
  replaced (mtime/content). Tampered checksum → `EXIT_CHECKSUM`, binary
  untouched. `--check` exit codes both ways.
- **Manual matrix:** Linux x86_64, Windows (running-exe rename-aside while
  TUI is open in another terminal), macOS arm64.

## 7. Explicit non-goals (for now)

- Signature verification (minisign/cosign) — SHA256-over-TLS matches the
  installers' trust model; revisit if threat model changes.
- Delta/patch updates, channels (beta/nightly), auto-swap on TUI start.
- Install receipts / axoupdater-style ownership tracking.
