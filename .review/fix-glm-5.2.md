## Checklist answers

**1. Correctness — OK.** `ResumeJournal::validate` (journal.rs:151-204) enforces every rule (url/total_size/chunk_size/offsets-length/per-offset-bounds/on-disk length/sha256/etag) and any mismatch discards journal + `.incomplete` (chunked.rs:135-140); I found no bypass that resumes into wrong bytes under the validator set actually available on HF (url embeds revision, LFS oid is stable). Crash-safety direction holds: stream bytes are written (`write_all`) before `journal.record` (chunked.rs:662-716), completion is recorded only after `flush`+`sync_all` (chunked.rs:741-743), and the mid-chunk page-cache window is documented and accepted. The zombie-record monotonic guard (journal.rs:232-241) is correct and, per my analysis of abort semantics, a late in-flight `record()` poll can only persist offsets for bytes genuinely on disk (safe). Foreign files (`len > total_size`) are rejected before validation (chunked.rs:108); a journal whose `.incomplete` shrank below the highest claimed byte is rejected (journal.rs:180-188). Residual (accepted, plan §2/§5): a same-size content change with *neither* sha256 *nor* etag resumes into mixed bytes, and — see finding 5 — a varying-CDN etag degrades cross-run resume to restart-from-zero.

**2. Concurrency — CONCERN (finding 1).** The terminal-leaf discipline *inside* the writer is honored: `record`/`flush` are fully synchronous, acquire no other lock, contain no `.await`, and the lock is poison-tolerant. The completion-record call site (chunked.rs:743) is clean. But the progress-tick call site (chunked.rs:716) runs **while the `progress` tokio mutex guard acquired at chunked.rs:698 is still held** (guard scope ends at :720), contradicting the adjacent comment, journal.rs module docs, plan §3.1, and the updated root AGENTS.md line 41 ("record() called outside every other lock"). No deadlock is possible (order is consistently progress→journal; record's critical section takes nothing else), but the sync write+fsync in `save()` now runs under the render-critical progress mutex. `wait_for_chunks`/`abort_all` interaction is sound: aborted futures never resume; an in-flight sync `record()` completes before the future is dropped and can only under-report.

**3. chunked.rs changes — OK.** Resume math is correct: `Range: bytes=(start+resume_offset)-stop` (chunked.rs:611), seek to `start+resume_offset` (chunked.rs:640), `chunk_downloaded` seeded at `resume_offset` so counters, short-stream math, and per-chunk speeds count only new bytes. The 206 assert (chunked.rs:624-632) is correct for corruption prevention but is an untested branch and a capability regression for range-ignoring servers (finding 3). Short-stream detection (chunked.rs:729-736) is correct for under-delivery — including the `advertised_size_mismatch` clamp scenario, where the straddling chunk now fails "short read" instead of being miscounted (the flipped e2e test survives because it asserts the *failure*, not the error message); it does not catch over-delivery (finding 4). Progress seeding is right: `downloaded = resumed_bytes`, `chunk_completed[i] = off == chunk_len(i)` (chunked.rs:175-190), global counter and pacing marker both seeded with `resumed_bytes` (the plan-review speed fix, chunked.rs:420-426), and journaled-complete chunks are skipped with no request (chunked.rs:426-432).

**4. mod.rs changes — OK.** The keep/delete matrix is correct: pair kept with a "resuming" status; `.incomplete` without journal deleted; orphan journal without `.incomplete` deleted (mod.rs:262-274). Transient, terminal, and 401 arms all keep both files (mod.rs:474-477, 485-487, 501-503). I found no path that leaves a journal able to corrupt a *later* run: every journal is re-validated against the later run's fresh probe (url/size/layout/validators) before any trust, and the discard path deletes `.incomplete` then journal (either crash order self-heals via prepare). Minor housekeeping: `handle_existing_file` returns `AlreadyExists` while leaving a stale `.incomplete`+journal pair on disk (the old prepare deleted the `.incomplete` unconditionally first) — no corruption, cleaned by TUI delete or a later attempt.

**5. Failure/cleanup paths — OK.** Success removes the journal after the rename (chunked.rs:264-270; crash-between leaves an orphan that prepare deletes). TUI delete removes the journal (downloads.rs:330-337, with unit pin at :1184-1194). The eager-journal guarantee is met for every test-pinned scenario: the flush at chunked.rs:168 precedes file creation and chunk spawn, so `server_500_mid_download` (zero completed chunks) still finds both files on disk. Note the plan's phrasing "probe-stage terminal failures included" is imprecise — a probe-stage failure never *creates* a journal (probe `?` precedes it); what holds is "any run past the probe leaves a journal, and pre-existing journals survive probe failures". No behavioral gap (finding 9, NIT).

**6. Tests — OK.** `journal_tests` pin the full validation matrix, round-trip, coalescing, monotonicity, and poison tolerance; `resume_worker_tests` pin the core byte-granular mechanism (non-zero, non-complete `resume_offset` → exact wire Range `bytes=1536-2047`, seek, untouched neighbors, journaled completion; clamped-end short stream → "short read" error) deterministically against an in-process hyper server; e2e `resume.rs` pins in-run retry, terminal-keep, cross-run resume, size-change discard, etag-change discard, and success-consumes-journal at the wire level; the two flipped `download_failures` assertions pin keep-on-terminal-failure. Determinism is sound: with `concurrent_threads = 2`, a chunk's completion record strictly precedes its worker's next semaphore acquisition, so ≥1 journaled-complete chunk is guaranteed before scripted request #4 fires — the exact race the plan review flagged. Scenario 1's assertion is order-independent (whichever of chunks 0/1 arrives first, both are journaled and both must be skipped). Remaining gaps: the 206-assert branch has no test (finding 3), and scenario 5 changes sha *and* etag together so the pure etag path is only covered by the unit matrix (minor).

Contract drift — CONCERN (finding 2).** The diff updated the root AGENTS.md tree entry but not the nested `src/AGENTS.md` §6, which still promises deletion semantics (lines 73 and 75) — it now contradicts both the code and the root doc. `tests/resume.rs`'s module header also still narrates the old behavior in the present tense (NIT). No *test* was left asserting deleted-on-failure: the only two such assertions were deliberately flipped with their doc context updated; `timeout_then_success` and the attempt-count test are probe-stage scenarios where no files are ever created, so their assertions still hold.

## Findings

1. **[MAJOR] `src/download/chunked.rs:698-720` — progress-tick `journal.record()` (line 716) runs under the `progress` mutex guard acquired at line 698** (guard lives to the end of the `if elapsed >= interval_secs` block). The comment at lines 712-715 ("Called OUTSIDE the progress-lock scope"), journal.rs module docs, plan §3.1, and root AGENTS.md line 41 all claim the opposite — the shipped code violates the diff's own pinned lock discipline, and the comment is factually false. No deadlock (order progress→journal is globally consistent; nothing acquires journal→progress), but the synchronous write+`fsync` in `save()` now executes while holding the render-critical tokio mutex, stalling sibling progress updates and the HUD once per coalescing interval. Fix: `drop(prog);` before the `journal.record(...)` call (or move the record outside the tick block) — one line.

2. **[MINOR] `src/AGENTS.md:73,75` — stale contract text not updated:** "restarts if .incomplete exists" and "transient errors consume a retry and delete .incomplete … terminal failure → mark_failed + .incomplete cleanup" now contradict the implementation, the plan §3.5, and the root AGENTS.md entry. In a repo where AGENTS.md files are load-bearing instructions, this is exactly the drift the diff should have swept.

3. **[MINOR] `src/download/chunked.rs:624-632` — the 206 assert is (a) an untested new branch and (b) a capability regression.** No unit or e2e test exercises a 200-answer-to-Range (the unit mock always answers 206; the e2e mock only bypasses range handling for Range-less requests). And a range-incapable server that passes the probe (Content-Length fallback) previously succeeded for single-chunk files (full body at offset 0 is correct there); it now fails every chunk. Justified for HF, but pin it with a test in `resume_worker_tests` and note the behavior change.

4. **[MINOR] `src/download/chunked.rs:729-736` — short-stream detection is one-sided.** An over-delivering 206 (body longer than the requested range) still writes past `stop` into the next chunk's territory with no error and the chunk "completes" (pre-existing behavior, but the fix's stated goal is closing silent-corruption holes). Cap writes to `chunk_total - chunk_downloaded` per item to close both directions.

5. **[MINOR] `src/download/journal.rs:70 vs :192-197` — doc/code mismatch on ETag severity.** The field doc says a mismatch is "only advisory"; `validate` hard-rejects (discard + restart from byte 0). The plan's framing is the accurate one. Consequence worth stating: on CDNs whose ETags vary per node across runs, cross-run resume silently degrades to restart-from-zero — the issue-#50 symptom in safety-preserving form. Consider wording the doc honestly and/or gating cross-run etag rejection on "sha256 also absent" (the LFS oid is the load-bearing validator).

6. **[NIT] `src/download/journal.rs:222-231` — `completed` is computed via `chunk_len(chunk_id)` before the `chunk_offsets.get_mut` bounds check;** an out-of-range chunk_id underflows `total_size - i*chunk_size` (debug panic) before the early return. Unreachable from current call sites; reorder the bounds check first.

7. **[NIT] `src/ui/app/downloads.rs:330-337`** — journal removal only on successful `.incomplete` removal: an orphan journal with no `.incomplete` yields an error and survives until the file's next download attempt cleans it. Similarly, crashed `save()`s can leave `<final>.incomplete.state.json.tmp` litter that nothing sweeps. Housekeeping only.

8. **[NIT] `tests/resume.rs:1-29`** — module header still narrates the unfixed transport in the present tense ("Today the transport destroys partial progress…"); post-fix this is stale narration.

9. **[NIT] Plan §2 "probe-stage terminal failures included" vs implementation** — a probe-stage failure never creates a journal; the guarantee actually delivered is "any run past the probe persists the journal eagerly, and pre-existing journals survive probe failures". Matches every pinned test; wording only.

## Summary

The core mechanism is sound and well-pinned: strict fail-safe journal validation against every fresh probe, byte-granular mid-chunk resume with correct wire math and seeded counters, keep-on-failure in all three retry arms, eager journal persistence, completion-fsync ordering (data-before-journal, under-report only), monotonic zombie guard, and the 206/short-stream hardening that also fixes a pre-existing silent-corruption hole the resume path would have amplified. Test determinism (the 2-worker pinning) is correctly reasoned. The one substantive change required is finding 1 — a one-line fix restoring the lock discipline the diff itself documents and asserts — plus the stale `src/AGENTS.md` sweep (finding 2). Findings 3-5 are small hardening/wording items worth folding in; none block the issue-#50 contract.

Residual risks: same-size content change with no sha256 and no etag resumes into mixed bytes (inherent, documented); varying-CDN ETags can force spurious restart-from-zero on cross-run resume (fail-safe but user-visible); mid-chunk journal offsets retain the theoretical power-loss page-cache window (accepted, backstopped by verification); over-delivering 206s remain undetected (finding 4).
