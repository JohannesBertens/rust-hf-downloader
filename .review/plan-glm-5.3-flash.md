# Plan Review: `plans/fix-issue-50-resume-downloads.md` (issue #50 resume downloads)

## Overall verdict: APPROVE-WITH-CHANGES

The journal design is sound and correctly sized. Two findings must land in the plan before implementation: the resume test scenarios 2 and 3 are not deterministic as set up (their "≥1 chunk journaled complete" assertions will likely fail *with* the fix, not just without it), and the plan never specifies when the journal file is first created, which scenario 2's `read_journal` hard-depends on.

## Findings

**1. [MAJOR] Scenarios 2 and 3 (run 1) are not deterministic — the plan's "all 5 scenarios turn green" claim is false as set up.**
Both scenarios run with the TestEnv default `concurrent_threads = 4` and put the scripted 500 at the 4th range request (`statuses: vec![200,200,200,500,200]`, tests/resume.rs:225-231 / :269-275). So chunks 0-3 are in flight concurrently when the 500 lands. The failing chunk's error path is pure CPU after response headers (`error_for_status()?` in `download_chunk_with_progress`, src/download/chunked.rs:355-360) and propagates to `wait_for_chunks` → `abort_all` in microseconds, while any surviving chunk must complete write_all → flush → `journal.record` (a temp-file + `sync_all` + rename save per §3.1) before its completion is journaled. The abort cascade wins that race most of the time, so `assert!(!completed.is_empty(), "at least one chunk must be journaled complete")` (tests/resume.rs:260) and `assert!(!completed_ranges.is_empty(), ...)` (tests/resume.rs:310-311) will likely fail against the *correct* implementation. Scenario 1 already demonstrates the deterministic pattern: `env.set("concurrent_threads", "2")` (tests/resume.rs:154) with the failure at requests #4/#5, so chunks 0/1 provably complete — the worker records before its semaphore permit is released — before the failing requests are even sent. Fix: apply the same `concurrent_threads = 2` setup (and optionally a later script slot for margin) to scenarios 2 and 3. This is a plan defect, not just a test nit, because the plan explicitly promises these tests pass with the design (§4).

**2. [MAJOR] Journal creation timing is unspecified; scenario 2 requires it to exist even with zero recorded chunks.**
§3.1 only persists via `record()` ("immediately ... on first record; otherwise at most once per 1 s") plus the completion record. Nothing says `download_chunked` writes an initial all-zero journal right after validation. But tests/resume.rs:67-69 panics unless the journal file exists after a terminal failure, and several realistic runs record nothing: probe-terminal failures (e.g. the 416 advertised-size-mismatch path in tests/download_failures.rs), or the race in finding 1. Specify in §3.2: save the journal once after validating and before spawning chunks (also keeps `prepare_download_paths`'s keep/delete pairing consistent after any crash — a `.incomplete` with no journal currently falls back to delete-and-restart, wasting real partial progress).

**3. [MINOR] Validation never cross-checks the `.incomplete` file length against the journaled offsets.**
§2 validates journal fields (including `chunk_offsets[i] ≤ chunk_len`) but not the data file. If the `.incomplete` is externally truncated/shortened while the journal survives, resume extends it with `set_len`, skips chunks whose offsets equal their length, and renames a hole of zeros into place. SHA256 verification (default-on) catches it; with `--no-verify` it is a silently corrupt final file. Cheap fix: add `file_len ≥ max(start_i + offsets[i])` to `validate`, discard otherwise. (Inference: no such test exists yet; low likelihood, high blast radius.)

**4. [MINOR] Short-stream under-fill is silently treated as chunk success — the exact failure domain of this issue.**
The worker returns `Ok` when `bytes_stream` ends cleanly before `stop - start + 1` bytes (clean FIN mid-body, or a range-clamping server — the mock itself clamps `end.min(served_total - 1)` in tests/common/mod.rs, which is how the 416/advertised-size scenario works). `chunk_downloaded < chunk_total` is never checked, so the chunk counts as done and the file-level size check passes (set_len made the file full-length). This is pre-existing, but the plan rewrites this worker and the resume path makes clamped/short responses more likely (resuming a range at an offset). Nearly free hardening: error when the stream ends with `chunk_downloaded < chunk_total`, and optionally reject non-206 responses to ranged requests.

**5. [MINOR] Lock discipline for `JournalWriter` should be written down as a terminal leaf, AGENTS.md-style.**
The design is correct: `std::sync::Mutex`, no await under the lock, sync fs IO follows the `REGISTRY_WRITE` precedent (AGENTS.md "TERMINAL LEAF" paragraph); it is not an `EngineState` field, so `docs_guards.rs::lock_hierarchy_documents_every_engine_mutex_field` is unaffected — which also means *nothing will force the documentation*. §3.5 updates the download/ prose but doesn't state the leaf rule (nothing acquired while held, no `.await`, callers may hold tokio progress locks when calling `record()` but never the reverse). Say it explicitly, or the next contributor will call an async fn under the journal lock.

**6. [NIT] Sync fsync+rename inside async chunk tasks.**
Each flush (first record, 1 s coalesce tick, every chunk completion) does a blocking temp-write + `sync_all` + rename on the tokio worker thread — up to ~25 serialized flushes near the end on real disks. Registry precedent accepts brief blocking IO and coalescing bounds frequency, so this is acceptable; note it in journal.rs docs so it isn't "optimized" into a spawn_blocking-per-record later without reconsidering the ordering guarantee.

**7. [NIT] Confirm the success-path journal removal ordering.**
`journal::remove` after `atomic_rename_with_retry_async` (§3.2) is correct; a crash between rename and remove leaves an orphan journal, which §3.3's "delete journal when `.incomplete` is missing" cleans on the next attempt of that file. Also note the all-complete-journal + failed-rename loop (Windows AV lock) converges: retry loads the journal, skips all chunks, retries the rename — worth one line in the plan since it's a new resume-shape.

## What is correct (checked, not assumed)

- **Design fit (checklist 1, 7):** per-chunk byte offsets in a sidecar journal is the right shape; the registry's scalar `downloaded_size` genuinely cannot represent holes (src/registry.rs semantics pinned by goldens in `registry/registry_tests.rs`), and per-chunk part files were rejected for the right reason (40 GB copy, lost instant rename). Under-report-only crash safety (data written before journal, coalescing only lags) is the correct direction. Validation rules (url/revision/total_size/chunk_size/etag-if-both-present, discard-don't-clamp) are proportionate; SHA256 backstop covers the etag-absent gap. Chunk math in tests/resume.rs matches `calculate_chunk_size` (src/download/chunked.rs:39-46): 100_000/8 → clamp(1024,4096) = 4096 → 25 chunks, tail 1_696.
- **Concurrency (checklist 2):** no new deadlock edges. `record()` is sync and leaf-only; chunk tasks hold tokio progress mutexes (level 3) when ticking and acquire the journal leaf inside — leaf acquires nothing, so no cycle. `wait_for_chunks` joins all tasks before the final rename, so no `record()` races `journal::remove`. `docs_guards.rs::module_dependency_dag` (no `crate::engine` in `src/download/**`) is unaffected by a private `journal.rs`.
- **Scope claims verified (checklist 5):** hf-cache sync really does inherit the fix — sync enqueues `base_path = staging` (src/cli/hf_cache/sync.rs:443-463) through the same `start_download`/`prepare_download_paths`, and `cleanup_staging` deliberately keeps failed `.incomplete` files (src/cache_layout.rs:774-780, test at :1522-1539) — journals now make that kept state actually useful. Cross-process locking deferral matches the registry's documented status. The registry-write-confinement docs guard only matches `registry_path|hf-downloads.toml`, so journal IO won't trip it.
- **Behavior changes (checklist 4):** keeping `.incomplete` + journal on transient retry, terminal failure, and 401 is correct and is the point of the issue; the partial bytes stay valid for that URL and are re-validated (url/size/etag) on resume. The contract flip in tests/download_failures.rs is coherent: exactly two disk assertions change (lines 109 and 183; plus the comment at :126), while registry (`Incomplete`, `downloaded_size = 0`), exit codes, and the success-path "no leftover" assertion (:308-309, rename consumes the file) are untouched.

## Summary

Approve the design; require amendments for findings 1 and 2 (both are small: reuse scenario 1's `concurrent_threads = 2` setup in scenarios 2/3, and specify an initial journal save after validation). Findings 3-5 are strongly recommended cheap hardening/documentation while the touched code is open. No simpler alternative preserves the single-preallocated-file + instant-rename layout; this is the standard control-file approach, not over-engineering.
